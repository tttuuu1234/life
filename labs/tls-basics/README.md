# tls-basics：HTTPSの「証明書」を体感する

HTTPSサーバーを2つ立てて、「証明書を誰が保証しているか」で、つながるかどうかが変わるのを確かめる実験です。Node.js 標準モジュールと `openssl` コマンドだけで動きます。学習用なので、本番では使わないでください。

## 起動

```bash
cd labs/tls-basics
bash make-certs.sh   # 証明書を certs/ に作る（git には入れない）
node server.js       # :8443 と :8444 でHTTPSサーバーを起動する
bash demo.sh         # 別ターミナルで実行する
```

## 登場するもの

| 名前 | ファイル | 役割 |
|---|---|---|
| 自己署名証明書 | `self-signed.crt` | 自分で自分を保証した証明書。「私は localhost です、私が保証します」状態。:8443 が使う |
| 認証局（CA） | `ca.key` / `ca.crt` | 証明書を発行して保証する役。本物の世界では Let's Encrypt や DigiCert など。ここでは自作の「Lab Root CA」 |
| 証明書署名要求（CSR） | `server.csr` | サーバーが CA に出す申請書。「このドメインの公開鍵はこれです、保証してください」 |
| サーバー証明書 | `server.crt` | CA が CSR を確認し、CA の秘密鍵で署名したもの。:8444 が使う |

証明書は「**このドメイン名の公開鍵はこれです**」と、**CA が署名して保証した書類**です。IDトークンが「この人は alice です」と認可サーバーが署名した書類だったのと同じ形です。

## demo.sh でやること

| 手順 | やること | 結果 | 理由 |
|---|---|---|---|
| 0 | `server.crt` の中身を見る | - | 誰の証明書か（subject / SAN）、誰が保証したか（issuer）、期限 |
| 1 | 自己署名の :8443 につなぐ | ❌ | 誰も保証していない |
| 2 | 自作CA発行の :8444 につなぐ | ❌ | curl が「Lab Root CA」を信頼していない |
| 3 | 「Lab Root CA を信頼する」と教えて :8444 につなぐ | ✅ | 信頼しているCAが署名している |
| 4 | 同じ設定で、偽サーバー :8443 につなぐ | ❌ | 信頼しているCAの署名がない |
| 5 | :8444 に `api.example.com` という名前でつなぐ | ❌ | 証明書に書かれた名前と違う |
| 6 | 検証をオフ（`-k`）にしてつなぐ | ✅ | 相手が誰でもつながってしまう |

手順2と3の違いが一番大事なところです。サーバーは同じなのに、**クライアントがどのCAを信頼しているか**だけで結果が変わります。

## ブラウザでやってみること

1. https://localhost:8443 を開く → 「この接続ではプライバシーが保護されません」などの警告が出ます。
2. https://localhost:8444 を開く → 同じく警告が出ます。ブラウザ（OS）が「Lab Root CA」を知らないためです。
3. 警告画面から証明書の中身を開くと、発行者（Lab Root CA）、対象（localhost）、有効期限が見られます。

普段のサイトで警告が出ないのは、OSやブラウザに「信頼するCAの一覧」（ルート証明書ストア）が最初から入っていて、サイトの証明書がその中のどれかに署名されているからです。

`ca.crt` をOSの信頼ストアに入れると :8444 の警告は消えますが、**試したら必ず削除してください**。`ca.key` を持っている人は、どのドメインの証明書でも作れてしまいます。

## Charles / Proxyman がHTTPSの中身を見られる理由

この実験の手順3と同じです。

1. ツールが自分のCAを作り、それを端末に「信頼する証明書」としてインストールさせる。
2. ツールが通信の間に入り、接続先ごとにそのCAで証明書をその場で発行して、本物のサーバーのふりをする。
3. 端末はそのCAを信頼しているので、警告が出ない。

TLSを破っているのではなく、「どのCAを信頼するか」を自分の端末で変えているだけです。攻撃者が同じことをできないように、信頼するCAを自分で決め打ちするのが **証明書ピンニング** です。
