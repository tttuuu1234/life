# oauth-pkce：OAuth 2.0（Authorization Code Flow + PKCE）と OpenID Connect を体感する

OAuth 2.0 の登場人物を、それぞれ別のサーバーとして動かす実験です。Node.js 標準モジュールだけで書いているので、`npm install` は要りません。
「写真印刷アプリ」が、あなたの写真サービスのパスワードを知らないまま「写真を見る権限」だけをもらう、という場面を再現しています。学習用なので、本番では使わないでください。

## 登場人物

| OAuthの用語 | このデモでは | ポート | ファイル |
|---|---|---|---|
| Resource Owner（データの持ち主） | あなた（alice） | - | - |
| Client（データを使いたいアプリ） | 写真印刷アプリ | 4002 | `client.js` |
| Authorization Server（ログインと同意を担当） | PhotoAuth（Googleのログイン/同意画面にあたる） | 4000 | `auth-server.js` |
| Resource Server（データを持つAPI） | 写真API（GoogleフォトのAPIにあたる） | 4001 | `resource-server.js` |

## 起動

```bash
cd labs/oauth-pkce
node start.js        # 3つのサーバーをまとめて起動する
```

ブラウザで **http://localhost:4002** を開きます。ターミナルには `[認可サーバー]` `[リソースサーバー]` `[クライアント]` の印付きでログが出るので、どのサーバーが何をしたかを追えます。

ログインは alice / `password` です。

## ブラウザでやってみること

1. **「PhotoAuth でログイン」を押す**
   画面の色とURLが変わり、アプリ（:4002）から認可サーバー（:4000）に移動します。パスワードを入力するのは認可サーバーの画面で、アプリはパスワードを見ません。
2. **「ログインして許可」を押す**
   アプリに戻ってきます。下の「何が起きたか」に、PKCEの値の生成から、リダイレクト、トークンの引き換えまでが順に記録されています。
3. **「写真を見る」を押す** → 200
   アクセストークンの `scope` に `photos.read` があるので、写真が返ってきます。
4. **「写真1を削除」を押す** → 403
   `photos.write` を許可していないので、スコープ不足で断られます。
5. **「連携を解除」してから、今度は「写真を削除する」にもチェックを入れてログインする**
   同意画面の権限が2つに増え、削除が200になります。
6. **同意画面で「拒否」を押す**
   `error=access_denied` 付きでアプリに戻ってきます。
7. **「トークンをリフレッシュ」を押す**
   ログイン画面を通らずに、新しいトークン一式が返ってきます。
8. **ログイン後の「ログインしているのは: alice（alice@example.com）」を見る**
   これが OpenID Connect（OIDC）の部分です。`scope` に `openid` を入れたので、アクセストークンと一緒に **IDトークン** が返ってきました。アプリはその署名・`iss`・`aud`・`exp`・`nonce` を確かめてから、ログインしているのが誰かを表示しています（「何が起きたか」の最後のステップに ✅ が並びます）。

## 流れを図で見る

アプリの画面にある「この流れを図で見る」（http://localhost:4002/flow）を開くと、9ステップのシーケンス図を1ステップずつ進めながら見られます。

- ログインしたあとに開くと、実際に通ったステップの番号が緑になり、説明カードに**さっきアプリが送受信した実際の値**（`code_verifier`、認可コード、トークンなど）が出ます。
- ステップ3〜4（ログインと同意）は、認可サーバーとあなたの間で起きるので、アプリには記録が残りません。アプリがパスワードも同意の操作も見ていないことが、図の上でも分かります。
- 図のファイルは `flow.html` で、実際の値は `client.js` が記録して `/flow.json` で返しています。

## curlで流れと攻撃を追う

```bash
bash demo.sh         # node start.js を起動した状態で、別ターミナルで実行する
```

このスクリプト自身が、アプリとブラウザの両方の役をやります。

1. PKCE の値（`code_verifier` / `code_challenge`）と `state` を作る
2. 認可リクエスト → 200（同意画面）
   2'. 登録されていない `redirect_uri` → 400（認可サーバーはリダイレクトせずに止める）
3. alice が許可 → 認可コード付きでアプリへリダイレクト
4. **攻撃**：認可コードを横取りした別アプリが、`code_verifier` を知らずに交換しようとする → 400
5. 本物のアプリが、認可コード + `code_verifier` で交換する → 200
6. 同じ認可コードを使い回す → 400（1回限り）
7. アクセストークンの中身を見る
8. 写真APIを呼ぶ → 200
9. 削除しようとする → 403（スコープ不足）
10. リフレッシュ → 200

後半は OIDC の「別のアプリ宛てのトークンでログインさせる」攻撃です。alice が、悪意のある「占いアプリ」（`fortune-app`）にもログインしたという設定です。

11. 占いアプリが alice のアクセストークンとIDトークンを手に入れる（IDトークンの `aud` は `fortune-app`）
12. ❌ アクセストークンでログインさせるAPI（`/api/login/access-token`）に、占いアプリのアクセストークンを送る → 200。**alice になりすませてしまう**
13. ✅ IDトークンを検証するAPI（`/api/login/id-token`）に、占いアプリのIDトークンを送る → 401（`aud` が自分宛てでない）
14. ✅ 同じAPIに、写真印刷アプリ宛ての本物のIDトークンを送る → 200

## コードの読みどころ

- `client.js` の `/login`
  `code_verifier`（アプリだけが知る秘密）と、それをSHA-256した `code_challenge` を作ります。認可リクエストで渡すのは `code_challenge` だけです。
- `auth-server.js` の `/authorize`
  `redirect_uri` が登録済みのものと完全一致しないと、リダイレクトせずに止めます。違うURLに認可コードを送ると、攻撃者に渡ってしまうためです。
- `auth-server.js` の `/token`
  受け取った `code_verifier` をハッシュして、最初に預かった `code_challenge` と一致するか確かめます。これがPKCEの本体です。認可コードは1回使ったら捨てます。
- `client.js` の `/callback`
  戻ってきた `state` が、自分が送ったものと同じか確かめます（CSRF対策）。
- `resource-server.js` の `authorize`
  トークンの署名・期限・宛先（`aud`）を確かめたうえで、**スコープ**を見て403を判断します。

## OpenID Connect（OIDC）の部分

OAuth 2.0 は「アプリに権限を渡す」仕組みで、「ログインしているのは誰か」をアプリに伝える決まりはありません。それを足したのが OIDC です。

| | アクセストークン | IDトークン |
|---|---|---|
| 役割 | 写真APIに見せる**許可証**（何をしてよいか） | アプリに見せる**身分証**（誰がログインしたか） |
| 宛先（`aud`） | 写真API（`photo-api`） | アプリ（`photo-print-app`） |
| 署名 | HS256（認可サーバーと写真APIが同じ秘密鍵を共有） | RS256（認可サーバーの秘密鍵で署名し、誰でも公開鍵で検証できる） |
| アプリは中身を見る？ | 見ない（写真APIに渡すだけ） | 見る（検証してからユーザーを決める） |

アクセストークンをHS256のままにしているのは、前のステップのコードをそのまま残すためです。IDトークンはアプリが検証するので、秘密鍵を渡さずに済むRS256にしています。

増えたエンドポイント（認可サーバー :4000）

- `GET /.well-known/openid-configuration`：ディスカバリー。各エンドポイントのURLや対応している署名方式の一覧
- `GET /jwks`：IDトークンを検証するための公開鍵
- `GET /userinfo`：アクセストークンを見せると、持ち主のプロフィールを返す

コードの読みどころ

- `auth-server.js` の `issueTokens`
  `scope` に `openid` があるときだけ `id_token` を作ります。`aud` はトークンを頼んだアプリの `client_id`、`nonce` はログイン開始時にアプリが送ってきた値です。
- `client.js` の `verifyIdToken`
  IDトークンで確かめる5つのことが並んでいます。署名（`/jwks` の公開鍵で）、`iss`（期待した発行者か）、`aud`（自分宛てか）、`exp`（期限内か）、`nonce`（自分が始めたログインのものか）です。
- `client.js` の `/api/login/access-token` と `/api/login/id-token`
  モバイルアプリが自社サーバーにログインするときの、危ない実装と正しい実装の比較です。アクセストークンは「誰宛てに発行されたか」をアプリが確かめられないので、別のアプリが手に入れたトークンでもログインが通ってしまいます。IDトークンは `aud` で弾けます。

## モバイルアプリだとどうなるか

このデモのクライアントはWebアプリですが、モバイルアプリでも流れは同じです。違うのは次の点です。

| | このデモ | モバイルアプリ |
|---|---|---|
| 認可サーバーの画面を開くもの | ブラウザ | `ASWebAuthenticationSession`（iOS）/ Custom Tabs（Android）。WebViewは使わない |
| `redirect_uri` | `http://localhost:4002/callback` | カスタムURLスキーム（`com.example.app:/callback`）やユニバーサルリンク / App Links |
| `code_verifier` の置き場所 | サーバーのメモリ | アプリのメモリ |
| トークンの置き場所 | サーバーのメモリ | Keychain / Keystore |
| client_secret | 使わない | 使わない（アプリに埋め込むと抜き取られるため。代わりにPKCEを使う） |

OIDCでは、アプリがIDトークンを受け取ったら、それを自社サーバーに1回だけ送ります。自社サーバーはこのデモの `/api/login/id-token` と同じ検証をしてから、自社のセッション（またはトークン）を発行します。

Flutterでは、`flutter_appauth` などのライブラリがこの流れをまとめてやってくれます。中で何が起きているかは、このデモの「何が起きたか」の記録そのものです。
