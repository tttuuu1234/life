Authorizationヘッダー

2026年10月10日

Authorizationヘッダーは、クライアントがサーバーに認証情報を渡すためのHTTPリクエストヘッダーである。値は<方式> <値>という書式で、先頭の方式（スキーム）が、続く値をどう解釈するかをサーバーに伝える。

Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
方式値の中身主な用途
BearerトークンOAuthのアクセストークン、JWT、セッションID
Basicユーザー名:パスワードをBase64にしたもの簡易的なAPI、社内ツール

Bearerの意味

Bearerは「持参人」の意味で、RFC 6750で定められている。「これを持ってきた者を、誰であれ正当な利用者として扱う」という性質を表しており、トークンが盗まれるとなりすましができる、という弱点もそのまま示している。

方式を省略した場合

Auth0、Firebase、Spring Security、AWS API Gatewayなど、標準に沿ったライブラリやサービスは方式を確認するため、Bearerを付けずに値だけを送ると401で拒否される。自前のサーバーで値をそのまま読んでいる場合は動くこともあるが、それはサーバー側が緩いだけである。

実装上の注意

  • 'Bearer $token'のように、方式と値の間に半角スペースを入れる。
  • サーバーがBearer込みの文字列を返す場合、アプリ側で重ねて付けるとBearer Bearer ...になり、401の原因になる。
  • 401のレスポンスに付くWWW-Authenticateヘッダーで、サーバーが期待する方式を確認できる。

JSON Web Token

2026年10月11日

JSON Web Token（JWT、「ジョット」と読む）は、JSONで表した情報に署名を付けて、改ざんされていないことを確かめられるようにしたトークン形式である（RFC 7519）。サーバーは表を引かずに、署名を検証するだけで「誰からのリクエストか」を判断できるため、APIのアクセストークンやOpenID ConnectのIDトークンに広く使われる。

構造

3つのパーツをピリオドでつないだ文字列である。

  • ヘッダー：署名方式（alg）など、トークンの扱い方を書く。
  • ペイロード：伝えたい中身（クレーム）。sub（誰か）、exp（有効期限）、iat（発行時刻）、iss（発行者）、aud（宛先）などの標準項目に加え、roleのような独自項目も入れられる。
  • 署名：「ヘッダー.ペイロード」と秘密鍵から計算した値。

ヘッダーとペイロードはBase64URLに変換しているだけで、暗号化されていない。誰でも元のJSONに戻して読めるため、パスワードなどの秘密は入れてはならない。

署名と検証

サーバーは、受け取った「ヘッダー.ペイロード」と自分の秘密鍵から署名を計算し直し、トークン末尾の署名と一致するかを確かめる。一致すれば、自分が発行したものであり、1文字も改ざんされていないことが分かる。

秘密鍵が必要なのは、計算方法（HMAC-SHA256など）が公開されているためである。秘密鍵を使わなければ、攻撃者はペイロードを書き換えたうえで署名も自分で計算し直せてしまう。秘密鍵を知らない攻撃者には、書き換えた中身に合う署名を作れない。逆に、秘密鍵が漏れると誰でも本物と同じJWTを作れるため、鍵は環境変数やキー管理サービスで厳重に管理する。

署名が一致しても、それだけでは足りない。次の確認もあわせて行う。

  • algがサーバーの想定どおりか。トークンが名乗る方式を信用すると、alg: none（署名なし）の偽トークンを通してしまう。
  • expが切れていないか。

署名方式

方式署名検証主な利用
HS256共通の秘密鍵同じ秘密鍵自前のサーバー
RS256 / ES256秘密鍵公開鍵Auth0、Firebase、Googleなど

なお、ピリオド3つの形式は署名付きJWT（JWS）のもので、中身を暗号化するJWE形式はピリオド5つになる。

途中で取り消せない

サーバーが確かめるのはトークン自身（署名と期限）だけなので、ログアウトしても、発行済みのトークンは期限が切れるまで使えてしまう。セッション認証のように表から消して無効にすることができない。これは、表を引かずに速く検証できることと引き換えのトレードオフである。そのため、アクセストークンは数分〜1時間程度の短命にし、リフレッシュトークンで取り直す設計にするのが一般的である。

モバイルアプリでの扱い

  • アプリは署名を検証しない（秘密鍵をアプリに入れられない）。受け取って保存し、Authorization: Bearerで送るだけ。
  • expを読んで、期限切れが近ければ先にリフレッシュする使い方はできる。
  • 保存先はKeychain / Keystoreにする。

手元で試せる実装は labs/token-auth/ にある。

OAuth 2.0

2026年10月13日

OAuth 2.0は、利用者のパスワードを渡さずに、別のアプリに「自分のデータへの限られた権限」を与えるための認可の仕組みである（RFC 6749）。たとえば写真印刷アプリが、利用者のパスワードを知らないまま「写真を見る」権限だけを受け取れる。権限は期限付きの鍵（アクセストークン）として渡され、範囲を絞れて、あとから取り消せる。

登場人物

用語役割例
リソースオーナーデータの持ち主。許可を出す利用者
クライアントデータを使いたいアプリ写真印刷アプリ
認可サーバーログインと同意の画面を出し、トークンを発行するGoogleのログイン/同意画面
リソースサーバートークンを検証し、許された範囲のデータを返すGoogleフォトのAPI

アプリが求める権限の範囲をスコープ（例: photos.read）という。同意画面に並ぶ項目がスコープで、発行されたアクセストークンに刻まれる。リソースサーバーはスコープを見て、足りなければ403を返す。

骨組みの流れ（Authorization Code Flow）

点線はブラウザを経由するやり取り（URLに載るので見られる前提）、色付きの実線はアプリとサーバーの直接通信である。認可サーバーはアプリに直接連絡する手段がないので、結果はブラウザのリダイレクト（redirect_uri）で返すしかない。そこで、鍵そのものではなく認可コード（引換券）を返し、鍵との交換は直接通信で行う。アクセストークンが短命なため、あわせてリフレッシュトークンも発行されることが多い。

守りの部品

部品ふさぐ穴
PKCE（code_verifier / code_challenge）認可コードを横取りされ、トークンに交換される
state攻撃者の認可コードを送り込まれ、攻撃者のアカウントにつながる（CSRF）。④で戻ってきた結果が、自分が①で始めたログインの続きかを確かめる
redirect_uri の完全一致戻り先を書き換えられ、認可コードが攻撃者のサイトに送られる

認証ではなく認可

認可サーバーの中ではログイン（認証）が行われるが、アプリが受け取るのは「何をしてよいか」を表すアクセストークンだけで、「誰がログインしたか」を伝える仕組みは仕様にない。ログインに使う場合は、IDトークンを追加したOpenID Connectを使う。

モバイルアプリでの注意

  • アプリは中身を解析されるため、client_secret を持てない（public client）。代わりに PKCE を必ず使う。
  • 同意画面は WebView ではなく、ASWebAuthenticationSession（iOS）や Custom Tabs（Android）で開く。
  • Flutter では flutter_appauth などがこの流れをまとめて扱う。トークンは Keychain / Keystore に保存する。
  • かつての Implicit Flow（URLにアクセストークンを直接載せる方式）は非推奨で、OAuth 2.1 では廃止された。

手元で試せる実装は labs/oauth-pkce/ にある。

OpenID Connect

2026年10月09日

OpenID Connect（OIDC）は、OAuth 2.0 の上に「ログインしているのは誰か」を伝える仕組みを載せた認証プロトコルである。OAuth 2.0 だけでは「このアクセストークンで何ができるか（認可）」しか分からないが、OIDC を使うと「このユーザーは誰か（認証）」も標準的な方法で取得できる。

OAuth 2.0 との関係

OAuth 2.0 は「アプリがユーザーに代わってリソースにアクセスする」ための認可フレームワークで、ユーザーの身元確認（認証）は仕様の範囲外である。そのため、各サービスが独自の方法でユーザー情報を返していた。OIDC はこの認証部分を標準化した拡張レイヤーにあたる。

OAuth 2.0OIDC
目的認可（何ができるか）認証＋認可（誰か＋何ができるか）
発行するトークンアクセストークンアクセストークン＋IDトークン
ユーザー情報仕様の範囲外IDトークンの標準クレームで取得
関係ベースのフレームワークOAuth 2.0 の上に載る拡張レイヤー

IDトークン

OIDC の中心にあるのがIDトークンである。これはJWT（JSON Web Token）形式で発行され、ユーザーの識別子（sub）、発行者（iss）、有効期限（exp）などのクレームを含む。アプリはこのトークンを検証することで、ユーザーが誰であるかを確認できる。アクセストークンがリソースへの「通行証」なのに対し、IDトークンはユーザーの「身分証明書」にあたる。

主な登場人物

  • OpenID Provider（OP）: ユーザーを認証してIDトークンを発行する側。Google、Apple、Auth0 などが該当する。
  • Relying Party（RP）: IDトークンを受け取ってユーザーを識別するアプリ側。「Googleでログイン」を実装しているアプリがこれにあたる。

認証フロー（Authorization Code Flow）

最も一般的なフローは以下のとおり。

ポイント

  • 「OAuth 2.0 = 認可」「OIDC = OAuth 2.0 + 認証」と覚えるとシンプル。
  • 「Googleでログイン」「Appleでサインイン」など、ソーシャルログインの裏側はほぼOIDCで動いている。
  • モバイルアプリやSPAでは、認可コードに加えてPKCE（Proof Key for Code Exchange）を併用するのが必須とされている。

Proof Key for Code Exchange

2026年10月13日

Proof Key for Code Exchange（PKCE、「ピクシー」と読む）は、OAuth 2.0 の認可コードが横取りされても、トークンに交換できないようにする仕組みである（RFC 7636）。「ログインを始めたアプリ」と「認可コードを交換しに来たアプリ」が同じであることを、使い捨ての合言葉で確かめる。

なぜ必要か

モバイルアプリの戻り先（カスタムURLスキーム）は、別のアプリも同じものを登録できるため、認可コードを悪意あるアプリに横取りされることがある。サーバー同士なら client_secret で本物のアプリかを確かめられるが、モバイルアプリは中身を解析されるので client_secret を持てない。PKCE はその代わりになる。

2つの値

値中身いつ・どこへ
code_verifierアプリがログインのたびに作るランダムな合言葉最後のトークン交換で、直接通信で初めて送る
code_challengecode_verifier をSHA-256でハッシュし、Base64URLにした値。合言葉の指紋最初の認可リクエストで、ブラウザ経由で預ける

③で認可サーバーは、受け取った code_verifier をハッシュし、①で預かった code_challenge と比べる。認可コードを横取りした攻撃者は合言葉を知らないので、ここで拒否される。

なぜ合言葉ではなく指紋を先に渡すのか

①はブラウザのURLを通るため、見られる可能性がある。合言葉そのものを載せると、認可コードと一緒に盗まれて意味がなくなる。ハッシュは不可逆なので、指紋を見られても合言葉は逆算できない。構造はパスワードハッシュと同じで、code_challenge がサーバーに預ける控え、code_verifier があとで照合する本体にあたる。

もとはモバイルアプリ向けに作られたが、現在は Web アプリを含むすべてのクライアントで使うことが推奨されている（OAuth 2.1）。

セッション認証

2026年10月10日

セッション認証は、ログインに成功したユーザーの状態をサーバー側で保持し、クライアントにはそれを引くためのセッションIDだけを渡す認証方式である。HTTPはステートレスなため、クライアントは以後のリクエストのたびにセッションIDを送り、サーバーはそれを手がかりに「誰からのリクエストか」を判断する。

仕組み

クロークの番号札にたとえられる。クライアントが持つのは番号札（セッションID）だけで、預けた中身（誰か、有効期限など）はサーバーのセッションストアにある。

セッションIDの届け方

ブラウザモバイルアプリ
受け取り方Set-Cookieヘッダーレスポンスのボディ
保存場所Cookie（ブラウザが管理）Keychain / Keystore
送り方Cookieヘッダーでブラウザが自動送信Authorization: Bearerで自分で付ける

ブラウザでCookieが選ばれるのは、自動で送信されることに加え、HttpOnly属性でJavaScriptから値を隠せるため（XSS対策）である。あわせてSecure（HTTPSのみ）やSameSite（CSRF対策）を付ける。ネイティブアプリにはこの恩恵がないので、ヘッダーで送るのが一般的である。URLにセッションIDを含める方法は、ログや履歴から漏れるため使わない。

長所と短所

  • 即時に無効化できる：ストアから行を消すだけで、ログアウトや全端末の強制ログアウトが即座に効く。トークン方式（JWT）に対する最大の利点である。
  • サーバーが状態を持つ：メモリに置くと再起動で全員ログアウトし、複数台構成でも共有できない。本番ではRedisやDBに置く。

セッションIDが盗まれた場合

攻撃者は、期限が切れるまでそのユーザーとしてアプリを操作できる（セッションハイジャック）。一方で、セッションIDからパスワードやDBの中身が分かるわけではない。被害を抑えるために次の対策をとる。

  • 推測できない十分長い乱数をIDにする。ログイン時には必ず新しいIDを発行する（セッション固定攻撃の対策）。
  • 有効期限を適切に設定し、異常を検知したらサーバー側でセッションを削除する。
  • パスワード変更や決済などの重要な操作では、パスワードを再入力させる。

モバイルアプリでの注意

  • SharedPreferences / UserDefaultsに平文で保存しない（flutter_secure_storageなどを使う）。
  • HTTPSが守るのは通信の途中だけ。ヘッダーをログやクラッシュレポートに出さない。
  • ログアウト時は、サーバーのセッションと端末のIDの両方を消す。401を受け取ったら保存済みのIDを消してログイン画面へ戻す。
  • iOSのKeychainはアプリを削除しても残るため、再インストール時に古いIDが残る場合がある。

手元で試せる実装は labs/session-auth/ にある。

認可コード

2026年10月13日

認可コード（authorization code）は、OAuth 2.0 で利用者が同意したあと、認可サーバーがアプリに返す引換券である。それ自体ではAPIを呼べず、認可サーバーのトークンエンドポイント（/token）でアクセストークンと交換するためだけに使う。

なぜ引換券を挟むのか

認可サーバーはアプリに直接連絡できないため、同意の結果はブラウザのリダイレクト（redirect_uri?code=...）で返すしかない。URLは履歴やログ、Referer ヘッダー、同じURLスキームを登録した別アプリなどから漏れうるので、鍵そのもの（アクセストークン）は載せず、単独では役に立たない引換券を載せる。鍵との交換は、ブラウザを通らない直接通信で行う。

盗まれても被害を抑える制限

  • 寿命が短い（数十秒〜数分）。
  • 1回しか使えない。使ったら認可サーバーが記録から消す。
  • 発行先のアプリ（client_id）と戻り先（redirect_uri）に紐づいている。
  • PKCE の合言葉（code_verifier）がないと交換できない。

トークンエンドポイントでの検証

認可コード自体は中身のないランダムな文字列で、認可サーバーは発行時に「誰が・何を・どのアプリに許可したか」を記録しておく（セッションIDとセッション表の関係と同じ）。交換のリクエストを受けると、次の順に確かめる。

確認不一致なら
記録にある認可コードか（未使用か）400 invalid_grant
期限内か400 invalid_grant
client_id が発行時と同じか400 invalid_grant
redirect_uri が発行時と同じか400 invalid_grant
SHA256(code_verifier) が預かった code_challenge と一致するか400 invalid_grant

すべて通ると認可コードを記録から消し、記録にある内容でアクセストークンを発行する。トークンに入るユーザーやスコープは、アプリが送ってきた値ではなく、認可サーバーの記録から作られる。

認証と認可

2026年10月10日

認証（Authentication、AuthN）は「あなたは誰か」を確かめること、認可（Authorization、AuthZ）は「あなたは何をしてよいか」を決めることである。多くのサービスでは、認証で利用者を確定させてから、認可でその人に許された操作かどうかを判定する。

認証認可
問い誰か何をしてよいか
例パスワード、生体認証、ソーシャルログイン管理者だけが削除できる、読み取り専用
失敗時のHTTP401 Unauthorized403 Forbidden

401と403

401は名前に反して「未認証」、つまり誰か分からない状態を表し、アプリはログインし直させる。403は「誰かは分かったが権限がない」状態を表し、ログインし直しても結果は変わらない。

認証を伴わない認可

認可は認証なしでも成り立つ。ホテルのカードキーは拾った人でもドアを開けられるし、「リンクを知っている人は閲覧可」の共有リンクもログインを求めない。OAuth 2.0のアクセストークンも同様に、持っていればAPIを呼べる。普段は「ログイン」という1つの体験の中で両方が起きるため混同されやすいが、別々の仕組みである。

認証の3要素

  • 知識：知っているもの（パスワード、PIN）
  • 所持：持っているもの（スマートフォン、セキュリティキー）
  • 生体：本人の身体的特徴（指紋、顔）

異なる要素を組み合わせる方式を多要素認証（MFA）という。

パスワードハッシュ

2026年10月10日

パスワードハッシュは、パスワードを平文で保存せず、元に戻せない（不可逆な）ハッシュ値に変換して保存する手法である。ログイン時は入力されたパスワードを同じ方法でハッシュ化し、保存された値と一致するかを確かめる。

ハッシュ化はサーバー側で行う

クライアントは平文のパスワードをHTTPSで送り、サーバーがハッシュ化する。クライアント側でハッシュ化すると、サーバーは受け取った値をそのまま比較することになり、そのハッシュ値が実質のパスワードになる。盗んだハッシュ値をそのまま送ればログインできてしまう（pass-the-hash）。

ソルト

ソルトは、ユーザーごとに生成するランダムな値で、パスワードに混ぜてからハッシュ化する。秘密にする必要はなく、ハッシュと一緒にDBに保存する。役割は、隠すことではなく、ユーザーごとにハッシュをバラバラにすることである。

100万人分のDBが漏れ、攻撃者がよく使われるパスワード1万個のリストで調べる場合を考えると、違いがはっきりする。

ソルトなしソルトあり
全員をまとめて調べる1万回の計算で済み、事前計算（レインボーテーブル）も使える1万回×100万人＝100億回。事前計算もできない
1人だけを狙う1万回1万回（変わらない）

つまり、ソルトが防ぐのは「まとめて」「作り置き」の攻撃であり、1人を狙った総当たりは防げない。

遅いハッシュ関数

1人を狙う総当たりには、1回のハッシュ計算をわざと遅くすることで対抗する。本人は1回計算するだけなので0.1秒程度の遅れは気にならないが、何億回も試す攻撃者には、その遅さがそのまま攻撃時間として効く。SHA-256のような高速なハッシュをパスワード保存に使ってはならないのはこのためである。

  • bcrypt：計算の繰り返し回数（コスト）で遅くする。
  • scrypt / Argon2：時間に加えて大量のメモリを必要とする（メモリハード）。コアは多いがコアあたりのメモリが少ないGPUでの並列攻撃を難しくする。

コストは、自分のサーバーで1回0.1〜0.5秒程度になるように調整するのが目安である。

ライブラリの出力形式

bcryptやArgon2のライブラリは、アルゴリズム、コスト、ソルト、ハッシュを1つの文字列にまとめて返す。開発者はこれをDBの1カラムに保存し、ログイン時は入力値と一緒にライブラリへ渡すだけでよい。ソルトの取り出しと比較はライブラリが行う。

$2a$12$R9h/cIPz0gi.URNNX3kh2OPST9/PgBkqquzi.Ss7KIUgO2t0jWMUW
 版  コスト  ソルト（22文字）    ハッシュ（31文字）

const stored = await bcrypt.hash(password, 12);   // 登録時
const ok = await bcrypt.compare(password, stored); // ログイン時

限界と補完策

どの方式でも、時間をかければ弱いパスワードは特定される。ハッシュの強化は「解かれるまでの時間稼ぎ」であり、その間に漏洩を検知して利用者にパスワードを変更してもらうことが重要である。

  • 利用者側：パスワードマネージャーで、長くランダムで、サイトごとに異なるパスワードを使う。
  • 開発者側：弱いパスワードの拒否、ログイン試行の回数制限、MFAの導入。DB以外の場所に置く秘密値（ペッパー）を混ぜる方法もある。
  • パスワード自体をなくすパスキーでは、サーバーは公開鍵しか保存しないため、漏れて困る秘密がない。

リフレッシュトークン

2026年10月11日

リフレッシュトークンは、期限が切れたアクセストークンを、ログインし直さずに取り直すためのトークンである。アクセストークンを短命にしても、利用者が頻繁にログインを求められないようにする役割を持つ。

アクセストークンリフレッシュトークン
役割APIを呼ぶアクセストークンを取り直す
寿命短い（数分〜1時間）長い（数日〜数か月）
よくある形式JWT（表を引かずに検証）ランダム文字列（サーバーの表で管理）
送り先すべてのAPI取り直し用のエンドポイントだけ
即時の無効化できないできる

セッション認証との関係

リフレッシュトークンは、サーバーの表で管理されるランダム文字列であり、仕組みはセッション認証のセッションIDとほぼ同じである。つまり、JWTを使う一般的な構成は「普段のリクエストはJWTで表を引かずに処理し、取り直すときだけ表を引く」という、両方式の組み合わせになっている。ログアウトや強制ログアウトでは、表からリフレッシュトークンを削除する。発行済みのアクセストークンは残り時間だけ使えるが、期限が切れた時点で取り直しができずに締め出される。

ローテーション

取り直すたびにリフレッシュトークンも新しいものに交換し、古いものを無効にする方式をローテーションという。さらに、無効にしたはずのトークンが再び使われたら盗難の可能性があるとみなし、そのユーザーのトークンをすべて無効にするリユース検知を組み合わせることもある。

モバイルアプリでの自動リフレッシュ

アプリは、APIが401を返したら自動で取り直し、失敗したリクエストを再送する。利用者はアクセストークンの期限切れに気づかない。

Flutterでは、Dioのインターセプターで実装するのが定番である。実装では次の点に注意する。

  • 多重リフレッシュを防ぐ：複数のAPIが同時に401になり、それぞれがリフレッシュすると、ローテーションにより2回目以降は無効になったR1を送ることになり、失敗して強制ログアウトされてしまう。リフレッシュは1回にまとめ、ほかのリクエストはその完了を待ってから再送する（QueuedInterceptorsWrapperなどを使う）。
  • 無限ループを防ぐ：リフレッシュ用のリクエストは、インターセプターを付けていない別のDioインスタンスで送る。
  • 取り直しに失敗したら：端末に保存したトークンを両方消して、ログイン画面に戻す。
  • 保存先：寿命が長く、盗まれたときの被害が大きいので、必ずKeychain / Keystoreに保存する。
