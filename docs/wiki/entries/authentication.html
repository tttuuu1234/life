OpenID Connect

2026年10月09日

OpenID Connect（OIDC）は、OAuth 2.0 の上に「ログインしているのは誰か」を伝える仕組みを載せた認証プロトコルである。OAuth 2.0 だけでは「このアクセストークンで何ができるか（認可）」しか分からないが、OIDC を使うと「このユーザーは誰か（認証）」も標準的な方法で取得できる。

OAuth 2.0 との関係

OAuth 2.0 は「アプリがユーザーに代わってリソースにアクセスする」ための認可フレームワークで、ユーザーの身元確認（認証）は仕様の範囲外である。そのため、各サービスが独自の方法でユーザー情報を返していた。OIDC はこの認証部分を標準化した拡張レイヤーにあたる。

IDトークン

OIDC の中心にあるのがIDトークンである。これはJWT（JSON Web Token）形式で発行され、ユーザーの識別子（sub）、発行者（iss）、有効期限（exp）などのクレームを含む。アプリはこのトークンを検証することで、ユーザーが誰であるかを確認できる。アクセストークンがリソースへの「通行証」なのに対し、IDトークンはユーザーの「身分証明書」にあたる。

主な登場人物

  • OpenID Provider（OP）: ユーザーを認証してIDトークンを発行する側。Google、Apple、Auth0 などが該当する。
  • Relying Party（RP）: IDトークンを受け取ってユーザーを識別するアプリ側。「Googleでログイン」を実装しているアプリがこれにあたる。

認証フロー（Authorization Code Flow）

最も一般的なフローは以下のとおり。

  1. RPがユーザーをOPの認可エンドポイントにリダイレクトする（scope=openid を指定）。
  2. ユーザーがOPでログインし、RPへのアクセスを許可する。
  3. OPが認可コードをRPにリダイレクトで返す。
  4. RPが認可コードをOPのトークンエンドポイントに送り、IDトークンとアクセストークンを受け取る。
  5. RPがIDトークンを検証し、ユーザーを識別する。

ポイント

  • 「OAuth 2.0 = 認可」「OIDC = OAuth 2.0 + 認証」と覚えるとシンプル。
  • 「Googleでログイン」「Appleでサインイン」など、ソーシャルログインの裏側はほぼOIDCで動いている。
  • モバイルアプリやSPAでは、認可コードに加えてPKCE（Proof Key for Code Exchange）を併用するのが必須とされている。
